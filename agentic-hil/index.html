Why an agent can write HiL code

Modern power converters switch at tens to hundreds of kilohertz, with transients that unfold on nanosecond timescales. To reproduce that faithfully, a hardware-in-the-loop simulator has to advance the model in steps under a microsecond — and inside that same microsecond it also has to solve the circuit state and drive the DAC/ADC conversion.

Only an FPGA can hold that deadline, which is exactly how commercial hardware-in-the-loop (HiL) equipment does it: discretize the continuous-time model, quantize it to fixed point, write it in Verilog, deploy it on an FPGA. Those machines run from several thousand to a few hundred thousand euros. What you pay for is the software: drag-and-drop modeling, automatic Verilog generation, and no need to know anything about FPGA programming to use the box.

So you are pushed into a choice:

  • buy the commercial HiL simulator — convenient, but expensive;
  • or work out the modeling and the HDL yourself — cheap, but it costs you people and time, and it may still come out wrong.

What makes the second path hard: hand-writing a circuit's continuous-time model as fixed-point, pipelined Verilog is digital-design work, and most power electronics engineers don't do it every day. Reaching for AI doesn't immediately help either — code-generation frameworks like VerilogCoder only see discrete digital logic. They have no notion of continuous physics, they don't track numerical stability, and they don't know a HiL solver has a hard real-time deadline hanging over it.

Our approach: let the AI do the tedious parts, inside one framework

Agentic HiL splits the job across three cooperating LLM agents:

  • Physics Agent — derives the state-space equations from the circuit topology, then discretizes and quantizes them to fixed point.
  • Hardware Agent — maps that model into flattened, low-latency Verilog and pushes it through synthesis.
  • Debug Agent — compares the synthesized RTL's simulated waveform against the floating-point reference, and when they disagree it goes back and fixes the fixed-point datapath itself, until they match.

What HiLCoder does

The framework in the paper is Agentic HiL; the installable skill that runs it is HiLCoder, which is on GitHub with the verified reference implementations. Each of the jobs below is slow and fiddly to get right by hand. Click through to see what it automates.

Automated fixed-point search

The Physics Agent runs a static range analysis on every state variable — e.g. the maximum possible inductor current — and picks the smallest Q-format bit-width that won't overflow or lose precision. That replaces the hours an engineer usually spends hand-calculating fixed-point scaling with a search that's re-run automatically whenever the circuit parameters change.

Output: model_fixed.c (Golden Reference) Format found: Q6.26

Waveform-driven automated debugging

Instead of an engineer scrolling through VCD waveforms by eye, the Debug Agent compares the synthesized RTL's simulated output against the Physics Agent's own floating-point reference. When the RMSE spikes — a sign of bit-misalignment, a missing sign-extension, or a register wrap-around — it walks backward through the Verilog's abstract syntax tree, finds the exact arithmetic node responsible, and rewrites the datapath definition automatically.

Checks: RMSE vs. golden reference Fixes: sign-extension, bit-alignment, overflow

Latency-first architecture optimization

Conventional digital-design agents chase throughput with deep pipelines — exactly the wrong instinct for a HiL solver, where the goal is minimizing tcalc, not maximizing clock frequency. The Hardware Agent instead maps independent state equations onto parallel DSP blocks and keeps the datapath flattened and combinational, so latency stays far below the real-time step Δt.

Automated timing-closure loop

The framework drives Xilinx Vivado in a loop: synthesize, check the critical path against Δt, and — if timing fails — restructure the parallelization instead of blindly adding pipeline stages, which would only reintroduce the latency problem. It keeps iterating until the design closes timing with room to spare.

What you need to build your own HiL simulator

The agents handle the modeling, the coding and the debugging. The toolchain and the hardware they target are still on you:

1
A workstation Runs the LLM agent pipeline, Vivado, and the simulation tools
2
LLM API access The Physics/Hardware/Debug agents are themselves LLM-driven
3
Xilinx Vivado Synthesis, implementation, and the timing-closure loop
4
iverilog / yosys Open-source RTL simulation for the AST waveform-tracing step
5
A simulation ground truth A floating-point reference model (e.g. PLECS) the Debug Agent checks the RTL against
6
Target FPGA board + user manual e.g. a Zynq-7020 board — the manual for pin mapping and clocking
7
DAC/ADC daughter board + user manual Only if you're closing the loop with real analog I/O rather than RTL simulation alone

Why the physics has to be in the loop

Here is the failure mode that makes this a physics problem and not a code-generation problem. Below is the buck converter's state-space model, integrated live in your browser with the same forward-Euler scheme and 50 ns step the generated RTL uses.

Turn off DCM handling and watch the inductor current: the solver keeps integrating past zero and produces a negative current the diode would physically block. Every waveform after that point is wrong, and nothing about the Verilog is syntactically broken — which is exactly why a boolean-correctness agent can't catch it.
