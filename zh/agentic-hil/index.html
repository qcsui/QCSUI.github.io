问题在哪

现代功率变换器的开关频率已经到了几十甚至几百 kHz,暂态过程发生在纳秒量级。 要在硬件在环(HIL)仿真里如实还原这些行为,就必须以亚微秒级的步长、并且是确定性地 推进模型 —— 这件事目前只有 FPGA 能稳定做到。

麻烦在于:把电路的连续时间物理模型手工翻译成定点、流水化的 Verilog, 是一项专门的硬件设计技能,而大多数电力电子工程师并不具备。 本来可以帮忙的 AI 代码生成工具 —— 比如 VerilogCoder 这类框架 —— 只理解离散数字逻辑,对连续物理、数值稳定性,以及 HIL 求解器必须满足的硬实时约束 没有任何概念。

思路

Agentic HIL 把这件事拆给三个协作的 LLM 智能体。Physics Agent 把电路拓扑转成离散化、定点化的状态空间模型;Hardware Agent 把这个模型映射成扁平化、低延迟的 Verilog 并推进综合;Debug Agent 则把综合后 RTL 的仿真波形与 Physics Agent 自己的浮点参考做对比, 自动修复定点数据通路,直到两者吻合。

输入 拓扑 + 指标
→
Physics Agent 状态空间 & Q 格式
→
Hardware Agent Verilog & 综合
→
Debug Agent RMSE & 自动修复
→
输出 经过验证的 HIL 仿真器

它具体能做什么

上面三个智能体各自负责的事情都很具体,而且单独拎出来靠人手工做都相当繁琐。 点开每个标签,看看它们实际自动化掉了什么。

自动搜索定点格式

Physics Agent 对每个状态变量做静态范围分析 —— 比如电感电流可能达到的最大值 —— 然后挑出既不溢出、又不浪费精度的最小 Q 格式位宽。 工程师原本要花几个小时手算定标,现在变成一次自动搜索, 而且电路参数一改就会自动重跑。

波形驱动的自动调试

不用人盯着 VCD 波形一行行看,Debug Agent 会把综合后 RTL 的仿真输出 和 Physics Agent 自己的浮点参考做对比。一旦 RMSE 突然变大 —— 这通常意味着移位没对齐、漏了符号扩展,或者寄存器发生了回绕溢出 —— 它就沿着 Verilog 的抽象语法树往回追,定位到出问题的那个算术节点, 然后自动改写数据通路的定义。

Checks: RMSE vs. golden reference Fixes: sign-extension, bit-alignment, overflow

以延迟为先的架构优化

常规的数字设计智能体习惯用深流水线去堆吞吐量 —— 这对 HIL 求解器恰恰是反的:这里要压的是 tcalc,不是把时钟频率拉高。 Hardware Agent 的做法是把相互独立的状态方程映射到并行的 DSP 单元上, 并让数据通路保持扁平的组合逻辑,从而把延迟压到远小于实时步长 Δt。

自动时序闭环

框架会循环驱动 Xilinx Vivado:综合、把关键路径和 Δt 做比较, 一旦时序不满足,就重新安排并行结构,而不是无脑加流水级 —— 后者只会把延迟问题重新引回来。这个循环会一直迭代,直到时序收敛并留有余量。

你需要准备什么

建模、写代码、调试这些事交给智能体,但工具链和目标硬件还是得你来准备:

1
一台工作站 跑 LLM 智能体流水线、Vivado 和仿真工具
2
LLM API 权限 Physics / Hardware / Debug 三个智能体本身就是 LLM 驱动的
3
Xilinx Vivado 综合、实现,以及时序闭环那一圈迭代
4
iverilog / yosys 开源 RTL 仿真,用于 AST 波形回溯那一步
5
一份仿真基准真值 浮点参考模型(比如 PLECS),Debug Agent 拿它来校验 RTL
6
目标 FPGA 板卡 + 用户手册 比如 Zynq-7020 板卡 —— 手册用于引脚映射和时钟配置
7
DAC/ADC 子板 + 用户手册 只有当你要用真实模拟 I/O 闭环、而不只是跑 RTL 仿真时才需要

为什么必须把物理放进环里

下面这个失效模式,正是"这是个物理问题,而不是代码生成问题"的原因。 这里是 Buck 变换器的状态空间模型,用和生成的 RTL 完全相同的前向欧拉格式、 50 ns 步长,在你的浏览器里实时积分出来的。

把 DCM 处理 关掉,盯住电感电流:求解器会一路积分穿过零点, 算出一个二极管在物理上根本不允许的负电流。从这一刻起后面的波形全是错的, 而 Verilog 在语法上挑不出任何毛病 —— 这正是只盯着布尔正确性的智能体抓不住它的原因。

    结果
